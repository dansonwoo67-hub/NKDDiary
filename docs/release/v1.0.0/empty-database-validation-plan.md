# v1.0.0 Empty Database Validation Plan

## Goal

Prove that the future schema baseline can initialize a disposable empty
Supabase environment to the same application-owned schema and security
contract as production, without copying production data.

No part of this plan has been executed yet.

## Preconditions

- baseline SQL has been generated and manually reviewed
- SQL contains no production data or secrets
- all 42 historical migration files have an archive manifest and checksums
- production schema inventory and fingerprint are available
- the disposable project/branch is confirmed not to be production
- the current Supabase CLI command syntax is checked with `--help`
- a cleanup owner and cost limit are defined

## Phase 1: Static review

1. Scan baseline SQL for:
   - UUID literals
   - email addresses
   - JWT/service-role keys
   - production project references
   - user content
   - destructive operations against existing objects
2. Confirm retired deletion objects are absent.
3. Confirm no duplicate function overload remains for capsule sealing.
4. Review every `SECURITY DEFINER` function, grant, policy, and search path.
5. Confirm migrations have unique version identifiers.

Exit gate: two-person review or explicit product-owner approval.

## Phase 2: Disposable empty environment

1. Create a new empty development branch/project.
2. Apply only the proposed v1.0.0 baseline.
3. Apply separately approved non-sensitive, idempotent seed/configuration.
4. Do not import production tables or Storage objects.

Exit gate: baseline applies once with no manual patching.

## Phase 3: Schema equivalence

Compare production and disposable environment inventories for:

- extensions and enum values
- tables and columns
- defaults and nullability
- constraints and indexes
- functions by identity arguments and body fingerprint
- triggers
- RLS enablement and policies
- grants/revokes
- Storage buckets and policies
- scheduled jobs

Allowlisted differences:

- migration-history rows
- project identifiers
- owners generated by the platform
- timestamps and environment-specific schedules explicitly documented

Exit gate: no unexplained schema difference.

## Phase 4: Security postflight

Verify:

- anonymous access cannot read private application data
- authenticated users see only their own/couple-space rows
- cross-account UUID access is rejected
- UPDATE policies include required SELECT access and `WITH CHECK`
- service-role code is server-only
- privileged RPCs reject unauthorized users
- private media requires valid signed access
- deleted/recycle-bin RPCs and table do not exist

Run Supabase database advisors when the execution stage has a supported CLI or
MCP tool.

Exit gate: no security error and no unexplained warning affecting release.

## Phase 5: Application verification

Against the disposable environment:

1. configure non-production environment variables
2. create only dedicated Susan/Niki test identities
3. run:
   - `npm test`
   - `npm run lint`
   - `npm run build`
   - `npm run test:e2e`
4. verify:
   - regular letter send/read
   - capsule create/open/image path when supported
   - withdrawal notice without body disclosure
   - notification unread predicate and read closure
   - Susan/Niki account isolation
   - memories, mood, calendar, and location flows

Expected current code gates:

- 73 test files passed
- 301 tests passed
- lint has 0 errors; 9 known image warnings
- production build succeeds
- 18/18 E2E tests pass

Exit gate: results match or exceed the v1.0.0 RC baseline.

## Phase 6: Repeatability

1. Destroy/reset the disposable environment.
2. Initialize it again from the same baseline artifact.
3. Repeat schema equivalence and a minimum release smoke suite.
4. Confirm checksums did not change between runs.

Exit gate: two clean initializations with no manual intervention.

## Failure and rollback rule

- Do not patch production.
- Do not mark the baseline as applied to production.
- Discard/reset only the disposable environment.
- Correct the proposed baseline in a new review cycle.
- Repeat validation from an empty state.

## Final approval evidence

The validation report must record:

- application commit SHA
- baseline migration SHA-256
- archive manifest SHA-256
- disposable environment identifier
- schema comparison result
- security advisor result
- test/lint/build/E2E outputs
- reviewer and approval timestamp

Only after this evidence is accepted may the baseline SQL become part of the
v1.0.0 release artifacts.
