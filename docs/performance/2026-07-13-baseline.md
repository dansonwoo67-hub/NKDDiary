## 可复现的结构基线

修改前，首页关键数据按顺序读取：身份与个人资料、月历、双方资料、最近写信位置；月历读取还会遍历用户与当天事件并读写通知。布局和首页分别调用身份与个人资料读取，造成重复等待。当天有事件时，通知路径会随“事件数 × 用户数”增加数据库往返。

修改后：

- `requireUser()` 使用 React 请求级缓存，同一次页面渲染中的布局与页面共享身份和个人资料结果，不跨请求、也不跨用户保存数据。
- 首页在身份确认后启动 5 个相互独立、具有明确数量或日期上限的读取，并通过 `Promise.all` 并行等待：双方资料、当前用户最近位置、当月信件、事件摘要、未读数。
- 当月信件强制使用月初与月末边界，只选择首页消费的 `author_id, letter_date, status, kind` 字段。
- 事件摘要统一限制为 `event_date <= 当月月末`；非循环事件同时限制为当月月初之后。循环事件必须保留历史起始日才能计算本月发生日，但不会读取未来月份才开始的事件。
- 页面读取不再生成提醒。事件提醒由数据库私有定时函数每 5 分钟检查一次，并以“接收人 + 事件 + 发生日期”保证幂等。
- 设置 `NKD_PERFORMANCE_LOGGING=1` 时，服务端会输出单次 `home_snapshot` 查询耗时，默认不记录。

## 本地验证

以下验证不会使用真实账号或记录密钥：

- 查询形状测试验证 31 天边界、事件查询月末上限、公开/私有状态隔离、并行启动与非法月份拒绝。
- 迁移静态测试验证提醒函数位于 `private` schema、固定 `search_path`、撤销客户端执行权、具备并发与重复写入防护。
- 完整测试、Lint、类型检查与生产构建结果由本任务提交前的验证记录为准。

## 部署前补测步骤

1. 在预览环境准备不含真实隐私内容的 A/B 测试账号。
2. 每项流程连续执行 3 次，排除首次冷启动后另记热路径中位数；冷启动数据单独保留。
3. 浏览器记录从导航/提交开始到首页主要内容可见且可交互；服务端同时开启 `NKD_PERFORMANCE_LOGGING=1` 对照 `home_snapshot`。
4. 只记录账号标签 A/B、时间和毫秒数，不记录邮箱、密码、Cookie、位置或信件内容。
