# NKD Diary CoupleOS 对标改造设计

日期：2026-07-25  
状态：等待用户审核  
实施路线：纵向分阶段，每阶段同时完成响应式 UI、业务规则、migration、RLS 和测试

## 1. 目标与边界

NKD Diary 是一个仅供两名固定用户使用的私人情侣空间。项目继续使用现有 Next.js、Supabase Auth、Postgres、Storage 和 Vercel，不重新初始化、不清空数据库、不删除现有数据。

CoupleOS 是信息架构、页面比例、视觉节奏和交互模式的参考。项目不复制 CoupleOS 名称、Logo、商标、代码、照片或专属品牌素材。

系统不提供公开注册、邀请配对、第三名成员、公开主页、点赞、收藏、标签、公开分享、下载导出、订阅、广告或 AI Insights。

## 2. 平台范围

第一阶段只开发一套响应式网页，不同时开发独立 iOS 客户端。后端和业务接口保持平台无关，为未来 iOS 客户端保留可能性。

必须完整支持：

- 375px：手机完整功能，单列布局，编辑 Modal 转全屏面板。
- 768px：平板完整功能，单列与双列混合布局。
- 1440px：桌面视觉母版，严格对标 CoupleOS 的结构和节奏。
- 1280×800、1440×900：额外桌面视觉回归。

全部核心页面和控件在三个宽度均须可达。Calendar 在手机端使用紧凑月历和选中日期事件列表。Journal、Mood、评论和 Memory 上传必须兼容软键盘、系统相册选择与浏览器本地图片压缩。

本阶段不做 PWA、原生 App、离线同步或触屏专属手势。

## 3. 全局信息架构与设计系统

固定底部导航包含：首页、回忆、日记、日历、设置。Mood 不占用底栏入口，从首页和 Memories 进入独立历史页。

页面共同骨架：

1. 奶油色页面背景。
2. 稳定居中的内容容器。
3. 衬线页面标题和无衬线正文。
4. 右上返回/主操作区。
5. 页面摘要区。
6. 主工作区。
7. 固定底部五项导航。

设计系统统一定义颜色、字体、容器宽度、边框、圆角、阴影、间距、输入框、按钮、卡片、Modal、Toast、下拉菜单、空状态、加载状态、错误状态、focus、hover、active 和页面切换动画。

Modal 在桌面和平板居中并允许内部滚动；在手机端使用全屏或接近全屏编辑面板。底部导航不得遮挡 Modal 的提交按钮或页面内容。

## 4. 账号、空间与访问控制

系统只有一个情侣空间和两个预创建的 Supabase Auth 账号。

新增 `spaces` 和 `space_members`。共享网站名称与在一起日期属于空间；主题属于个人。

所有业务表逐步增加 `space_id`。RLS 同时校验登录身份、空间成员关系、作者/创建者身份和时间窗口。误创建的第三方 Auth 用户不能进入空间或读取任何数据。

兼容迁移顺序：

1. 新增 nullable 字段和新表。
2. 建立固定空间及两名成员关系。
3. 回填现有业务数据。
4. 运行一致性检查。
5. 增加约束、索引和新 RLS。
6. 完成兼容验证前不删除旧字段。

## 5. 登录

登录页只保留邮箱密码登录、忘记密码、密码显隐、登录中状态和可访问错误提示。

删除注册、第三方登录、邀请配对、订阅、定价和营销入口。站点名称来自共享空间配置或安全的初始配置，不在组件内写死。

未登录用户只能访问登录和密码恢复流程。

## 6. 首页

首页沿用 CoupleOS Dashboard 的模块节奏，但用私人空间功能替换邀请和社交内容。

首页包含：

- 共享网站名称和双方昵称、头像。
- 在一起天数与下一纪念日。
- Mood 快速发布。
- 最近普通日记。
- 最近普通评论、正文评注与回复。
- 未来七天日历事件。
- 最近 Memories 内容和独立 Memory 照片。
- 今日日记、Mood、Calendar、Future Journal 快捷入口。

现有距离、今日新知和紧凑月历保留代码与数据，移至次级区域，后续再决定是否长期显示。

首页查询应并行化，不建立重复聚合表，不在读取页面时生成通知。

## 7. Mood

Mood 是独立业务类型，并替代 CoupleOS 的 Glimmer。

规则：

- 每位用户每天可发布多条。
- 每条最多 15 个 Unicode grapheme cluster。
- 不支持图片、评论、标签、点赞或分享。
- 作者发布后 24 小时内可编辑删除。
- 24 小时后锁定。
- 另一位用户只能查看。

入口位于首页、Memories 黄色快速输入区和独立 Mood 历史页。所有入口调用同一验证和权限逻辑。

## 8. Journal 与 Future Journal

Journal 与 Memories 完全分离。Journal 页面提供“日记 / 未来日记”双视图。

### 普通日记

- 每位用户每个 Asia/Shanghai 自然日最多一篇。
- 两位用户同日可各写一篇。
- 标题可选，正文必填。
- 每篇最多一张压缩照片。
- 不保存情绪标签。
- 不增加标签、点赞、收藏或分享。
- 作者发布后 24 小时内可编辑、删除和替换照片。
- 24 小时后锁定。
- 另一位用户始终不能修改。

Journal 首页显示日记总数、本月数量、Future Journal 状态、写作提示和最近条目。保留写作提示，但不保存连续签到。提示只用于启动写作，不自动写入正文或生成标签。

### Future Journal

- 设置未来解锁时间。
- 解锁前隐藏正文。
- 解锁后允许另一位用户阅读。
- 不占普通日记额度。
- 保留现有数据和已经存在的更具体约束。

## 9. 评论、正文评注与回复

普通评论最多 200 个 grapheme cluster，单层按时间展示。作者 24 小时内可编辑删除，之后锁定。日记锁定后仍可新增评论。

正文评注继续针对正文片段，独立于普通评论。评注回复保持单层。评注和回复作者只能管理自己的内容；日记锁定后仍允许新增。

时间限制必须同时存在于页面、Server Action/API、数据库函数或 RLS 以及自动化测试中。

## 10. Memories

Memories 不聚合 Journal 或 Future Journal。

时间线聚合：

- Mood。
- 独立 Memory。
- 纪念日。
- 生日。
- 约会。
- 旅行。
- 标记为重要的生活、待办或其他 Calendar 事件。

Calendar 的纪念日、生日、约会和旅行自动进入 Memories。生活、待办和其他事件默认不进入，开启“这是重要时刻”后进入。时间线保存业务引用，不复制 Calendar 记录。

### 独立 Memory

字段包括空间、作者、标题、日期、描述、可选照片、创建时间、修改时间和锁定时间。

- 每条最多一张照片。
- 作者 24 小时内可编辑删除。
- 24 小时后锁定。
- 另一位用户只能查看。

照片最长边不超过 1600px，优先 WebP，目标不超过 500KB，超过 800KB 拒绝。不保存原图，不复制其他来源图片。

Memories 页面包含顶部统计、Mood 快速输入、全部/心情/照片/重要日子/独立回忆筛选、年月筛选、正倒序、时间线、图片卡片和统一的新建 Memory Modal。

## 11. Calendar

事件包含标题、描述、开始/结束日期时间、全天状态、类型、地点、重复规则、重要标记、创建者、创建时间和修改时间。

类型包括约会、旅行、纪念日、生日、生活、待办和其他。支持月视图、今日、下一项、即将发生、重要日期、新建、查看、编辑和删除。

创建者可编辑删除自己的事件，另一位用户只能查看。Calendar 不上传照片，也不接入公开日历。

## 12. Settings

Settings 包含：

- 两人共享的网站名称。
- 当前用户昵称和头像。
- 另一位成员资料展示。
- 在一起日期。
- Asia/Shanghai 时区。
- 个人浅色、深色、跟随系统主题。
- 修改密码。
- 站内通知偏好。
- 紧凑月历设置。
- 退出登录。

两名成员均可修改共享网站名称，系统记录最后修改者和时间。主题是个人偏好，不影响另一位用户。

删除邀请、邀请码、解绑、第三人、邮件通知、订阅、博客、公开帮助、删除账号和 CoupleOS 品牌介绍。

## 13. 站内通知

不接入邮件服务。站内通知覆盖新日记、评论、正文评注、回复、Future Journal 解锁和近期重要事件。

通知不得在页面读取过程中生成。采用写入事件时派生或幂等后台任务，避免事件乘成员的串行 N+1 查询。

## 14. 图片与 Storage

分别管理头像、日记照片和独立 Memory 照片。对象使用私有访问和短期 signed URL，不生成永久公开地址，不提供下载按钮，不使用付费图片转换或第三方压缩 API。

头像最长边不超过 512px、目标 150KB，每位用户只保留当前头像。旧公开头像 Bucket 先审计和设计迁移方案，未经确认不直接改动。

## 15. 搜索引擎与隐私

所有私人页面设置 `noindex`、`nofollow`，`robots.txt` 禁止抓取，不生成 sitemap。页面不展示 Storage 路径、密钥或永久公开链接。

浏览器无法绝对阻止已授权用户截图或保存已加载内容，产品不得声称具有该能力。

## 16. 性能

重点优化首页并行查询、重复 Supabase 请求、Calendar 范围查询、signed URL 缓存、客户端组件数量、Modal 按需加载、图片体积和页面切换。

每阶段记录 TTFB、请求数量、Supabase 请求数、RSC/JS 体积、图片传输体积、控制台错误和 hydration 错误。开发服务器数据只用于发现问题，最终以生产构建和部署环境为准。

## 17. 测试与验收

自动化测试覆盖：

- 两名固定成员与第三方拒绝。
- 日记每日额度和 24 小时边界。
- 评论 200 grapheme。
- Mood 15 grapheme、多条发布和锁定。
- Memory 单图、聚合、权限和锁定。
- Calendar 类型与重要事件聚合。
- Future Journal 解锁。
- RLS、图片压缩、路由保护。

人工与 E2E 响应式验收覆盖 375px、768px、1440px 的登录、首页、Journal、Future Journal、评论、Calendar、Mood、Memories 和 Settings。发布门禁要求 lint、TypeScript、单元测试、E2E 和 build 全部通过。

## 18. 实施阶段

### 阶段 A：安全基线

创建改造分支，记录当前 Git 和 migration 状态，建立回滚与数据备份要求。

### 阶段 B：空间和权限

新增空间、成员关系、`space_id` 回填、索引和 RLS，验证现有数据不丢失。

### 阶段 C：设计系统、登录和全局外壳

完成三段响应式令牌、底部导航、Modal、Toast、表单、登录和全局状态。

### 阶段 D：首页与 Mood

完成首页真实聚合、Mood 快速发布和历史页。

### 阶段 E：Journal

完成普通日记、Future Journal、评论、正文评注、回复、单图和锁定规则。

### 阶段 F：Memories

完成独立 Memory、Mood/Calendar 聚合、筛选、排序和时间线。

### 阶段 G：Calendar

完成完整事件模型、响应式视图、CRUD、重复规则和 Memories 聚合。

### 阶段 H：Settings 与通知

完成共享名称、双方资料、主题、密码、站内通知和头像方案。

### 阶段 I：Storage、性能和安全

完成私有图片、signed URL、请求优化、SEO 保护和全量权限审计。

### 阶段 J：最终回归

完成三个宽度、两名成员、第三方拒绝、生产构建和部署前检查。每阶段结束后停止并等待用户验收，不自动进入下一阶段。

## 19. 明确不在本规格内

- 独立 iOS/Android 客户端。
- PWA 和离线同步。
- Google Calendar 双向同步。
- 邮件通知。
- AI 分析。
- 公开分享、导出和下载。
- 多成员、多空间和商业化。
